# Choosing a theme

The app follows the OS. It now also lets the user overrule it — with the app's own Light or Dark, or one of the named palettes shipped beside them (Catppuccin, Dracula, Everforest, Gruvbox, Monokai, Nord, One Dark, Rosé Pine, Solarized, Tokyo Night) — from the settings menu in the sidebar footer, beside Usage.

The choice is stored in `localStorage` under `orchestrate:theme`, and **System is stored as the absence of a key** rather than as the string `"system"`. That way a later change to what System resolves to reaches people who never touched the control, which is the whole point of their not having touched it. Nothing about the theme goes through the Rust side: it is a preference about how this window looks, it has no bearing on agents or worktrees, and giving it a place in the persisted app state would have meant an IPC round trip before the app could decide what colour to be.

The resolution happens **in script, not in CSS**. `theme.svelte.ts` reduces the preference to the one value the stylesheet cares about — a theme's name — and writes it to `<html data-theme>`; `theme.css` then has one block per theme. The alternative — keeping `@media (prefers-color-scheme: dark)` and layering `[data-theme]` overrides on top of it — needs every dark value written twice, once inside the media query and once outside, and gets the precedence wrong in one direction or the other unless both are complete. Resolving first is what makes an override possible at all without that duplication.

Because CSS can no longer work it out alone, an **inline script in `app.html`** applies the stored value before the first paint, so the window never flashes white on launch. It duplicates two lines of `theme.svelte.ts` deliberately: waiting on the module means waiting on the bundle, which is exactly the flash it exists to prevent. The two must agree on the storage key and the attribute, and both say so.

**`color-scheme`** — the part of theming the stylesheet cannot reach, read by native form controls, by scrollbars where the engine draws its own, and by the canvas behind the document, and without which a dark window flashes white on overscroll — is declared **in each theme's block**, not written by the store. With two themes either place would have done; with sixteen, a theme that says which way it goes in the same block as its colours cannot be added half-way.

While the preference is System, a `matchMedia` listener keeps it following the OS live, so a machine that switches at sunset switches the app with it rather than at the next launch.

The control is a **menu**, grouped System / Light / Dark, opened from the same quiet full-width footer row as Usage beside it. Picking a theme **leaves the menu open**: the app repaints behind it, which is the only way to judge a palette, and with this many to try, closing after each would be the entire cost of trying them.

Each row carries a **swatch painted with that theme's own tokens** — a `<span data-theme="dracula">` filled with `var(--surface)`, `var(--accent)` and `var(--success)`. That is why the theme blocks are selected as `[data-theme=…]` rather than `:root[data-theme=…]`: a preview that is the theme itself cannot drift from it the way a hand-kept list of preview colours would.

The palettes live in **`themes.css`**, separate from `theme.css`, and restate only colour tokens — a theme changes what the app is coloured, never how big or how fast it is. Each is the upstream project's published palette mapped onto this app's roles; the roles with no counterpart upstream (the tint behind a diff line, the fill behind a running agent) are derived from the palette's own colours, which is why the alpha values repeat across themes and the hexes never do.

An unrecognised stored name — a theme since removed, a value from a newer build — reads as **System** rather than as a window with no colours. The pre-paint script does not do that check, because the list of themes lives in the module it exists to avoid waiting for; an unknown name paints as Light for the one frame before the module replaces it, and a known one is already right.

Considered and rejected: **persisting through the Rust side**, covered above. **A settings window** to hold this one preference, which is where a third and fourth preference would push it, but not where one belongs. **Skipping the pre-paint script** and accepting a flash, which is cheap to avoid and looks broken. **A `"system"` value written to storage**, which freezes today's meaning of the default into every existing install. **Generating the palettes from a few anchor colours at runtime** with `color-mix`, which reads as one line per theme and looks it: the tuned hexes a palette is known for would survive only where the formula happened to agree with them.
