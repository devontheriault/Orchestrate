# Delivered means nothing held

The Delivered Bucket was decided from the merge record alone: `merged_at` set and the Agent not Running put it under Delivered. That was cheap and wrong at the edges. Resume a Delivered Agent, let it write a file or Commit again, and it stayed in Delivered — filed under the pile you are done with while holding work the Project had never seen. The Agent's own diff pane said so plainly ("Committing again brings it back", since the new commits are unmerged), but the sidebar contradicted it, and the sidebar is what you scan.

`CONTEXT.md` recorded the old rule as deliberate: bucketed on the record "because the sidebar has the Agent and not its diff". That reasoning stands — the sidebar genuinely does not have the diff — but it argued for the wrong conclusion. The answer is not to bucket on less; it is to get the sidebar the one fact it is missing.

So the Bucket is now chosen in this order: **Running** wins outright, an Agent with no merge record sits under its **State**, a Merged Agent **holding work** the Project has not got goes back under its **State**, and only what is left is **Delivered**. Back to its own State rather than always Completed, so a Merged Agent that was Resumed and then Failed reads as Failed.

"Holding work" is two things, not one: something uncommitted in the Worktree, *or* commits at the tip that no Project branch contains. Only the second survives a Commit, and the second is the case the user actually hits — Resume, work, Commit, and the Worktree is clean again while the work is still nowhere near the Project. A `git status` check alone would have called that Delivered.

The cost is a git call the Agent record cannot answer, which is what the old decision was avoiding. It is bounded two ways. It is asked **only of Agents with a merge record**, so it scales with how many Agents you have already Merged rather than with how many you have. And it is asked **only on events that can have changed the answer** — app refresh, a Turn ending on a Merged Agent, and a Commit — never on a timer. A Merged Agent's Worktree only changes because the Agent ran, and a Turn ending is an event the app already receives, so polling would buy nothing. The check itself is deliberately much cheaper than `agent_diff`: no patch, and no scratch index, since `git status` reports untracked files on its own and only `git diff` needs the intent-to-add.

Failures read as **holding nothing**, so a Worktree that has gone missing or a git that declines to answer leaves the Agent where its merge record puts it instead of a sidebar row claiming work that may not exist. This is why `branches_containing_head` now returns a `Result`: an empty list means no branch has the tip, which *is* unmerged work, and conflating that with "git could not say" would invent work out of an error.

Considered and rejected: **calling `agent_diff` per row**, which already answers this and several other questions, but builds up to 512 KB of patch text per Agent to do it. **Persisting a flag on the Agent** when it is Resumed or Commits, which turns a fact git already knows into state the app has to keep true, and would go stale the moment anything touched the Worktree from a terminal. **Dropping Delivered back to Completed literally**, which would file a Merged-then-Failed Agent under Completed. **Uncommitted changes only**, which is the narrower reading of the same complaint but misses the Resume-and-Commit case entirely — the one that prompted this.
