# Landing Agent work onto the Project

An Agent Commits to its own branch, `cw/agent-<id>`, and there the work sat. Getting it into a real branch meant leaving the app for a terminal — the single most common thing the app sent its user elsewhere to do. **Land** closes that: a Committed Agent's branch is merged into a branch the user picks, from a control beside Commit on the Agent itself.

Land is **the only thing that writes to the Project**, and it is always the user's action. An Agent never touches the Project — that invariant is unchanged and is what makes Worktree isolation worth having. What changed is the wording: `CONTEXT.md` used to say the Project's working tree is never touched, which was true only because nothing wrote to the Project at all. It now says the app writes to the Project when the user asks, and names the one case where a Land reaches the working tree rather than just a branch ref.

The merge is **`--no-ff`**. The Agent's branch is the record of what one Agent did, and a merge commit keeps it identifiable as a unit. Squashing throws away its individual commits, and rebasing rewrites their hashes so the branch no longer matches what landed — which breaks the Base story, where everything an Agent produced is meant to read as one diff against the commit it was cut from.

When the target branch is **not** the one checked out, the merge runs in a **throwaway worktree**: `git worktree add` the target, merge there, remove it. `git merge` requires its target checked out, and the alternative — switching the user's working tree to the target and leaving them on it — would make a Land silently relocate the user. The app already knows how to create and remove worktrees, so this costs almost nothing. When the target *is* the checked-out branch, git will not check it out twice, so the merge runs in place; that is the one case where a Land needs the Project's tree to be clean, and the only case where the precondition applies.

A **conflict aborts**. `git merge --abort` leaves the Project byte-identical to before and the colliding files are named for the user to resolve in their own tools. This app has no merge tool, and leaving a half-merged working tree behind would put the Project somewhere the app has no way to get it back out of.

A Land **does not end the Agent**. Reap is the only action that destroys anything and deliberately takes two clicks; destroying a Worktree as a side effect of a merge would smuggle that past the user. The Land is recorded on the Agent along with the branch it went to, as a fact like the Base rather than a new state — Commit is not a state either.

Considered and rejected: **a full git client** in the app (staging, branches, fetch/pull/push, history), which was scoped out after it became clear one button covered the actual friction, and which would have traded three of this project's five principles for surface nobody had asked for. **A ref-level fast-forward** (`git fetch . <agent-branch>:<target>`), which avoids the worktree dance but only works when the merge is a fast-forward, and we want a merge commit. **Offering `cw/agent-*` branches in the target picker**, which would make Agent-onto-Agent landing an accident rather than a decision, and which is the multi-agent coordination V1 defers. **Auto-Reaping on a successful Land**, covered above. **Leaving a conflicted merge in place** for the user to finish, which is defensible only for an app that can show and resolve conflicts, and this one cannot.
